## M1 是什么（先读完再动手）

M1 不是再学一个新协议。它是把 W2–W5 串成一次完整闭环：

```text
观察流量
→ 识别参数和签名
→ 用 Python 在本地后端复现请求
→ 关掉实验开关，确认 App 还能正常用
```

本周要亲手做完的业务链：

```text
登录 → 拿到虚构 Token → 查询 Profile → 创建测试订单 → 接收 WS 事件
```

防护不要一次全开。每次只动一个开关，记下「开了之后多出来的失败现象」。已经有的能力（HTTPS、Pinning、时间窗口、nonce）本周是 **验收**，不是推倒重来。

简单反调试本周只做 **可开关的检测 + 记录**。默认不要 `exit()`。W7 还要继续用 Frida，把进程杀掉会挡下一周。

不要一开始处理：越狱检测、secret 混淆、第三方 App、全局 SSL Kill。它们属于 W11 / W19。

## 执行 1：补齐 Profile，跑通业务链

### 1.1 目标

后端 `GET /api/profile/<user_id>` 已存在。App 需要能点一次并显示 JSON。

固定测试数据（虚构）：

```text
user_id:   demo-user-001
password:  demo-password
order_id:  order-001
amount:    10
```

### 1.2 App 改动要求

- 增加 **Profile** 按钮。
- 请求 `GET {baseURL}/api/profile/{user_id}`。
- 继续走现有 `APIClient` 和 Pinning delegate，不要另开忽略证书的 Session。
- 文本区显示 HTTP 状态和 body。
- 未填 user_id 时提示，不要发空路径。

本周不必给 Profile 加签名，除非你已经看到后端要求签名。当前后端 Profile 是未签名 GET。把「未签名」写进报告，这是特征，不是缺陷隐瞒。

### 1.3 真机流程

Pinning 先按你要观察的方式设置。直连回归用 Pinning ON、代理关。

```text
1. 启动 ./ .venv/bin/python3 app.py
2. Health → 200
3. Login → 200，保存 token
4. Profile → 200，display_name
5. Create Test Order → 200，status=created
6. Connect WS → 出现 tick 帧
7. Disconnect WS
```

全部在 XR 上点一遍，不要只 curl。

### 1.4 验收标准

- [x] App 能查询 Profile。
- [x] 登录、下单、WS 仍可用。
- [x] 五个步骤都有一份成功输出（可截进笔记，脱敏）。

### 1.5 失败处理

- Profile 404：user_id 必须是 `demo-user-001` 或 `demo-user-002`。
- WS 无帧：先 Login；Pinning+代理会在证书层失败。
- 后端连不上：不要用 `127.0.0.1`；确认 SAN 仍是当前局域网 IP。

### 3.1 文件


若 00.2 已经写过一份，本周 **覆盖或扩写同一路径**，不要两份互相打架。必须覆盖：

```text

```

每个接口用同一模板：

```text
接口：

认证方式：
必填字段：
字段含义：
签名输入：
响应结构：
失败条件：
是否签名：
Pinning 是否影响：
```

### 3.2 签名规则（照抄，不要改）

```text
canonical =
    "user_id=" + user_id
    + "&timestamp=" + timestamp
    + "&nonce=" + nonce
    + "&action=" + action

sign = HMAC-SHA256(local-demo-secret-v1, canonical)
```

- login 的 action 是 `login`，另带 `password`
- order 的 action 是 `order`，另带 `order_id`、`amount`
- health、profile、WS 当前无此签名

### 3.3 脱敏

- 不写真实账号、真实 Token、第三方包名
- 虚构 `demo-token-...` 可保留，标明测试值
- 不贴 `ca.key` / `server.key`

- [x] 能指出哪些接口要签名、canonical 怎么拼。

## 执行 4：Python 离线复现

### 4.1 目标

不打开 App，只靠脚本让 **自己的后端** 接受 login 和 order。

文件：

```text
/Users/weideshun/Desktop/SignDemo/scripts/reproduce/sign_login.py
/Users/weideshun/Desktop/SignDemo/scripts/reproduce/sign_order.py
```

可从 `backend/scripts/sign_local_request.py` 拆，不要复制到 App 同步目录。

默认连 `https://127.0.0.1:5443`，校验 `certs/ca.crt`。Python 3.14 若报 CA key usage，可关 `VERIFY_X509_STRICT`，并在脚本注释里写明这是练习 CA。

真机地址仍是局域网 IP；脚本在 Mac 上跑可以用 127.0.0.1。

### 4.2 脚本必须做的事

```text
读取测试 user_id
生成 timestamp
生成 nonce
按固定顺序拼接 canonical
计算 HMAC-SHA256
发送请求
检查响应 ok
```

`sign_login.py` 成功应打印虚构 token。  
`sign_order.py` 应自己签一次 order；不要依赖 App 里的 nonce（nonce 只能用一次）。

只允许打：

```text
127.0.0.1
当前 Mac 局域网 IP
```

禁止把脚本指向任何第三方或公网。

### 4.3 验证

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
./.venv/bin/python3 app.py
```

另开终端：

```bash
cd /Users/weideshun/Desktop/SignDemo
./backend/.venv/bin/python3 scripts/reproduce/sign_login.py
./backend/.venv/bin/python3 scripts/reproduce/sign_order.py
```

错误 timestamp、错误 sign、重复 nonce 应分别失败，和执行 2 的表一致。

### 4.4 验收标准

- [x] login 脚本被后端接受。
- [x] order 脚本被后端接受。
- [x] 能故意造失败请求并解释原因。
- [x] 脚本不包含真实账号。
