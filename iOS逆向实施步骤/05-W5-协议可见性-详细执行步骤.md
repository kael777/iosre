## 这些协议是什么（先读完再动手）

W4 解决的是「HTTPS 里证书信谁」。W5 解决的是「同样加密，不同协议在代理里能看见什么」。

抓不到明文，不一定是 Pinning。先问：流量走的是哪一种协议。

| 协议 | 底层 | 你在本周要亲眼看到的 | 代理大致能看见什么 |
|---|---|---|---|
| HTTP/1.1 | TCP | 现在的 `/api/health`、`/api/login` | 明文 Header + JSON（解密后） |
| HTTP/2 | TCP | 同一套接口，Header 压缩、连接复用 | 取决于代理是否支持 h2 |
| WebSocket | TCP，先 HTTP 升级 | 登录后持续推送测试事件 | 握手是 HTTP；之后是帧 |
| QUIC / HTTP/3 | **UDP** | 确认 SignDemo **当前不用它** | 系统 HTTP 代理通常看不见 |
| gRPC | 一般跑在 HTTP/2 上 | 一个带 `.proto` 的 Ping | 二进制，没有 schema 很难读 |

不要混的几件事：

```text
1. Pinning 拦的是「证书对不对」
2. 协议可见性拦的是「代理能不能解码这种传输」
3. QUIC 走 UDP，iOS 的 Wi-Fi HTTP 代理只管 TCP
4. gRPC 看起来像乱码，是因为 protobuf 是二进制，不是因为「加密更强」
```

本周观察 WebSocket / HTTP/2 时，把 SignDemo 的 **Pinning 关掉**。否则 mitmproxy 仍会在证书那一层失败，你会误以为是协议问题。实验结束后把 Pinning 再打开。

不要一开始处理：越狱检测、反调试、secret 混淆、第三方 App 协议还原。它们属于后续周次。

## 执行 1：后端增加 WebSocket

### 1.1 目标

在现有 HTTPS 服务上增加：

```text
WS /ws/events
```

连接后每隔 5 秒推送：

```json
{"ok": true, "type": "tick", "service": "SignDemo", "time": 1730000000}
```

可用虚构 token 查询参数，例如：

```text
wss://192.168.1.8:5443/ws/events?token=demo-token-...
```

第一阶段不要做复杂鉴权。token 能读到就记下；校验失败只返回关闭原因即可。

### 1.2 建议实现

Flask 开发服务器本身不带 WebSocket。在 `backend` 虚拟环境里安装：

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
source .venv/bin/activate
pip install "flask-sock>=0.7,<1.0"
pip freeze | grep -i -E 'flask-sock|simple-websocket' >> /tmp/signdemo-ws-pkgs.txt
```

把依赖写进 `requirements.txt`，不要手改 `.venv` 路径。

在 `app.py` 的 `create_app()` 里挂路由，例如 `/ws/events`。推送循环必须能被客户端断开打断，不要卡死整个进程。

`python app.py` 仍要同时提供：

```text
http://0.0.0.0:5000
https://0.0.0.0:5443
```

不要把后端再挪回 `SignDemo/SignDemo/`。

### 1.3 Mac 本机验证

先启动：

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
source .venv/bin/activate
python app.py
```

另开终端。可用 `websockets` 或浏览器扩展，至少用 Python：

```bash
python - <<'PY'

import websockets

ctx = ssl.create_default_context(cafile=str(ca))
url = "wss://127.0.0.1:5443/ws/events?token=demo-local"

async def main():
    async with websockets.connect(url, ssl=ctx) as ws:
        for _ in range(3):
            print(await ws.recv())

asyncio.run(main())
PY
```

若未安装 `websockets`：

```bash

```

预期：连续收到至少 2 条 `type=tick` 的 JSON。

- [x] `GET /api/health` 的 HTTP 和 HTTPS 仍然成功。

## 执行 3：HTTP/2 对照

### 3.1 目标

看清 HTTP/1.1 和 HTTP/2 的差别。当前 `python app.py` 的 Flask 开发服务器是 **HTTP/1.1**。不要假设开了 HTTPS 就是 HTTP/2。

### 3.2 先记录 HTTP/1.1 基线

```bash
curl -vk --http1.1 --cacert /Users/weideshun/Desktop/SignDemo/backend/certs/ca.crt \
  https://127.0.0.1:5443/api/health
```

记下：

```text
ALPN / HTTP 版本：
是否看到 Connection: keep-alive：
Header 是否明文一行一个：
```

### 3.3 用 Hypercorn 临时提供 HTTP/2

Flask `app.run()` 不适合作为本周 HTTP/2 实验床。另装：

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
source .venv/bin/activate
pip install "hypercorn>=0.17,<1.0"
```

停掉占用 5443 的 Flask HTTPS，只保留 HTTP `:5000` 或暂时全停，然后：

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
source .venv/bin/activate
./.venv/bin/hypercorn app:app \
  --bind 0.0.0.0:5443 \
  --certfile certs/server.crt \
  --keyfile certs/server.key
```

Hypercorn 0.18 没有 `--alpn-protocol`。带上 `--certfile` / `--keyfile` 后会自动做 ALPN，客户端要 h2 就走 HTTP/2。不要加 `--quic-bind`，那是 UDP/HTTP3，属于执行 4。

验证：

```bash
curl -vk --http2 --cacert certs/ca.crt https://127.0.0.1:5443/api/health
```

预期出现 `HTTP/2` 或 `ALPN: h2`。

再用 App（Pinning 按需要开关）点 Health。若证书指纹没变，Pinning ON 直连仍应成功。

### 3.4 对照表

| 项目 | Flask `:5443` HTTP/1.1 | Hypercorn `:5443` HTTP/2 |
|---|---|---|
| 传输层 | TCP | TCP |
| curl 看到的版本 | | |
| Header | | |
| mitmproxy 能否解密 | | |
| 多路复用 | 无（一请求一等待） | 同一 TCP 连接上并行流 |

用自己的话写一句：HTTP/2 仍是 TCP，所以系统 HTTP 代理仍可能工作；它和 QUIC 不是一回事。

### 3.5 验收标准

- [x] 能证明当前默认 Flask 是 HTTP/1.1。
- [x] 能用 Hypercorn 打出至少一次 HTTP/2 health。
- [x] 能说明多路复用是「一条连接多条流」，不是「更加密」。
- [x] 实验结束后知道如何回到 `python app.py`（WS 还在 Flask 上）。

### 3.6 失败处理

- curl 仍是 HTTP/1.1：确认 `--http2` 且 Hypercorn 配了 ALPN `h2`。
- App 失败但 curl 成功：Pinning 指纹是否仍指向同一张 `server.crt`。
- WS 在 Hypercorn 下坏了：本周允许 HTTP/2 实验时暂停 WS，记在笔记里，结束后回到 Flask。

## 执行 4：确认没有 QUIC，写下降级结论

### 4.1 目标

本周 **不要求** 给 SignDemo 上完整 HTTP/3 栈。要证明的是：

1. 现在的 SignDemo / Flask / Hypercorn 走 TCP，不走 UDP 443。
2. iOS Wi-Fi 里填的 HTTP 代理只管 TCP，所以 QUIC 不是「Pinning 太强」，而是「代理根本接不住」。
3. 练习用的降级开关就是：客户端只用 `NSURLSession` 的 TCP HTTPS，不启用 HTTP/3。

### 4.2 怎么确认没有 UDP

后端跑着、App 点 Health / WS 时，在 Mac 上：

```bash
lsof -nP -iUDP | grep -E '5443|443' || true
lsof -nP -iTCP:5443 -sTCP:LISTEN
```

预期：5443 是 TCP listen；没有进程在 UDP 5443/443 上为 SignDemo 服务。

可选：

```bash
sudo tcpdump -n -c 20 host 192.168.1.8 and port 5443
```

应看到 `tcp`，不是 `udp`。

### 4.3 判断顺序（抓不到时用）

```text
是否有 UDP 流量？
是否使用了系统代理？（系统代理通常只管 TCP）
代理是否支持该协议？
客户端是否自动降级到 TCP？
服务端是否根本没开 H3？
```

当前答案应接近：

```text
没有 UDP
用了系统代理也只能代理 TCP
mitmproxy 不是 QUIC 代理
NSURLSession 默认走 TCP HTTPS
服务端没有 H3
```

### 4.4 降级开关（练习口径）

在笔记里写明：

```text
SIGNDEMO_HTTP3=0（默认）
App 不配置 HTTP/3
后端不监听 UDP
需要抓包时走 TCP HTTPS / WS
```

不要为了「看起来高级」强行上 Caddy/quic-go。那会把 W5 拖成运维周。

### 4.5 验收标准

- [x] 能证明 5443 是 TCP。
- [x] 能用自己的话解释：QUIC ≠ HTTPS 抓不到。
- [x] 能说明系统 HTTP 代理对 UDP 无效。
- [x] 记下「若以后真开 H3，先关 H3 再抓包」。

## 执行 5：最小 gRPC 和 .proto

### 5.1 目标

加一个能跑的 Ping，学会用 `.proto` 读字段编号。本周 **不要求** 把 gRPC 编进 iOS App。Python 客户端即可。

### 5.2 文件

```text
/Users/weideshun/Desktop/SignDemo/backend/proto/signdemo.proto
```

最小内容示例：

```protobuf
syntax = "proto3";

package signdemo;

service SignDemo {
  rpc Ping (PingRequest) returns (PingReply);
}

message PingRequest {
  string user_id = 1;
  int64 timestamp = 2;
}

message PingReply {
  bool ok = 1;
  string service = 2;
  int64 time = 3;
}
```

字段 `1`、`2`、`3` 就是编号。二进制里先出现的是这些编号，不是 JSON 的 key 名。

### 5.3 服务和客户端

安装：

```bash
cd /Users/weideshun/Desktop/SignDemo/backend
source .venv/bin/activate
pip install "grpcio>=1.60,<2" "grpcio-tools>=1.60,<2"
```

生成代码：

```bash
python -m grpc_tools.protoc \
  -I proto \
  --python_out=proto \
  --grpc_python_out=proto \
  proto/signdemo.proto
```

单独起一个 gRPC 服务，建议端口 **5445**，证书仍用 `certs/server.crt` / `server.key`，不要占用 5443。

Python 客户端对 `127.0.0.1:5445` 调 `Ping`，`user_id=demo-user-001`。

记下：

```text
请求字段编号：
user_id 的 wire 类型：string / length-delimited
返回 ok / service / time 的编号：
```

可用 `protoc --decode` 或客户端打印来对照。不要把真实账号写进去。

### 5.4 验收标准

- [x] `signdemo.proto` 存在。
- [x] Python 客户端能收到 `ok=true`。
- [x] 能指出至少一个字段编号。
- [x] 能说明：没有 `.proto` 时，抓到的 gRPC body 不像 JSON 那么好读。

### 5.5 失败处理

- `ALPN` / HTTP/2 报错：gRPC 需要 h2。确认用的是 grpc 服务器，不是 Flask。
- 证书失败：客户端加载 `ca.crt`，或本机测试临时关校验并在笔记标明。
- `ModuleNotFoundError: proto`：把 `proto/` 加入 `PYTHONPATH`，或生成到包内。

## 和 W4 的关系

| W4 | W5 |
|---|---|
| 证书信谁 | 协议让你看见什么 |
| Pinning ON 时代理失败 | 观察 WS/H2 时先把 Pinning 关掉 |
| mitmproxy 要带练习 CA | 同样，否则上游 TLS 先失败 |
| 真机不用 `127.0.0.1` | WS / gRPC 同样不用 |
| 后端不放进 App 同步目录 | 继续 |

观察结束后把 Pinning 开关打开，确认 Health 在代理下再次失败。这是防止 W5 把 W4 的结论冲掉。
